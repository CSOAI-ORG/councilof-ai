## 1. What the issue is

**Ours.** `CSOAI-ORG` opened #2150 on 2026-08-19: "Extension proposal: signed-receipts/v1 — a
did:web key-trust convention for §8.4 + signed task-outcome receipts". It is not an A2A
maintainers' proposal and nothing in it is *decided* by the A2A project. State: **open, no
maintainer comment, no label, no linked PR in a2aproject/A2A**. The question it asks the project
is only venue: is the experimental extension tier the right path.

What it proposes (spec + reference interceptor at `CSOAI-ORG/a2a-signed-receipts`, Apache-2.0):

1. a key-trust convention for §8.4 AgentCard signing: the JWS `kid` is a DID URL, resolved to a
   DID document (reference profile `did:web` → `/.well-known/did.json`), no new registry;
2. a signed receipt object (RFC 8785 canonical JSON, `content_id`, Ed25519 reference algorithm)
   an agent MAY attach at `Task.metadata["signed-receipts/v1"]`;
3. a normative register: a receipt is evidence of what was claimed and when — never a
   certification, endorsement or conformity mark.

## 3. What the current spec (v1.0.1) requires of an AgentCard implementer

Fields are from `message AgentCard` in `a2a.proto`. REQUIRED per `google.api.field_behavior`.

| field | status | note |
|---|---|---|
| `name`, `description`, `version` | REQUIRED | `version` is the agent's own version |
| `supportedInterfaces[]` | REQUIRED | `{url (absolute HTTPS), protocolBinding (JSONRPC / GRPC / HTTP+JSON), protocolVersion, tenant?}`; first entry is preferred; each MUST accurately declare transport and URL (§8.3.1) |
| `supportedInterfaces[].protocolVersion` | REQUIRED | **`Major.Minor`: "0.3", "1.0"** — not "1.0.0". Requests carry `A2A-Version: 1.0`; an absent header means 0.3 |
| `capabilities` | REQUIRED | `streaming?`, `pushNotifications?`, `extendedAgentCard?`, `extensions[]` (`AgentExtension{uri, description, required, params}`) |
| `defaultInputModes[]`, `defaultOutputModes[]`, `skills[]` | REQUIRED | skill = `{id, name, description, tags[] (all REQUIRED), examples[], inputModes[], outputModes[], securityRequirements[]}` |
| `provider{url, organization}`, `documentationUrl`, `iconUrl`, `securitySchemes{}`, `securityRequirements[]` | optional | |
| `signatures[]` | optional | `AgentCardSignature{protected, signature, header?}` — JWS over JCS (RFC 8785) of the card minus `signatures`, minus default-valued non-required fields; protected header MUST carry `alg`, `kid`, SHOULD `typ: "JOSE"`, MAY `jku` |
| top-level `protocolVersion`, `url`, `preferredTransport`, `additionalInterfaces` | **gone at 1.0** | 0.3 fields; both moved into `supportedInterfaces` |

Discovery path: `https://{domain}/.well-known/agent-card.json` (IANA well-known registration in
the spec; `agent.json` is the 0.2 legacy path). Content type in the spec examples is JSON; we
serve `application/a2a+json` via `_headers`.

Signatures: MAY sign; clients SHOULD verify one when present. §8.4 leaves the key-trust root open
— that gap is exactly what #2150 fills with `kid` = DID URL. The `a2a-python` SDK (v1.1.3) base
model sets no `extra="forbid"`, so non-proto keys on a card are ignored, not rejected; a gRPC
reconstruction drops them, which is the canonicalisation trap `scripts/adapters/agent_card_jws.py`
already names.

Extensions: declared in `capabilities.extensions[]`; clients opt in with the `A2A-Extensions`
service parameter; URIs SHOULD carry a version and MUST change on a breaking change.

## 4. Audit of our cards (before this lane)

`public/.well-known/agent-card.json` (served at councilof.ai, 200, `application/a2a+json`) and
`public/.well-known/agent.json` (alias). No route in `functions/api` serves them; they are static.

| finding | severity | fix |
|---|---|---|
| `supportedInterfaces` named `/api/assess` (HTTP+JSON) and `/mcp` (JSONRPC). Probed 2026-09-05: `/mcp` answers `message/send` with `-32601 method not found`; `POST /api/assess/v1/message:send` is 404 and `/api/assess` is a keyword screener. **Neither speaks A2A.** §8.3.1 violated. | the real gap | new `functions/api/a2a.ts`: a v1.0 JSON-RPC door (SendMessage → Message with `totals.lid` verbatim + derived rows; every other method the spec-mapped error). Card now names only that door. |
| `protocolVersion` "1.0.0" on interfaces | wrong format | "1.0" (Major.Minor) |
| top-level `protocolVersion` ("1.0.0" in agent-card.json, **"0.3.0" in agent.json**) and `url` | 0.3 fields on a 1.0 card, and the two paths disagreed | removed; `agent.json` is a byte-identical alias, enforced by `scripts/test_agent_card.py` and `functions/api/a2a.test.ts` |
| non-proto keys `note` (on an interface), `endpoint` (on a skill), `documentation` (duplicate of `documentationUrl`) | drift | folded into descriptions/removed. Kept, deliberately and documented: `catalogUrl`, `doi`, `explicitly_not` |
| `documentationUrl` pointed at the card itself | circular | `https://councilof.ai/llms.txt` (200) |
| `signatures` absent | MAY, not MUST | still absent — **no server-side key is present in CI to sign** (board-sign is OIDC; the card key `did:web:csoai.org#card-attestation-1` is not provisioned to a workflow). `agent_card_jws.py` emits the signing input and verifies; signing stays owner-gated. Never fake it. |
| `capabilities.extensions` does not declare `signed-receipts/v1` | correct as is | we do not attach receipts on any task yet, so declaring it would be a name promising what the code lacks. Declare only when `/api/a2a` actually emits one. |
| `did:web:councilof.ai` in SPEC.md examples resolves to a DID document whose `id` is `did:web:csoai.org` | spec-repo inconsistency | owner-gated: SPEC examples should use `did:web:csoai.org`, or a councilof.ai DID document should carry its own id |
| `public/.well-known/agents.json` (custom `csoai.agents-discovery/0.1`) is in master but 404 live | not A2A; deploy lag | none here |
