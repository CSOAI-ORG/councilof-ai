# Charter and working-group completion plan

The delivery target is one usable public participation path: inspect a source, understand its limits, identify the responsible forming group, prepare a revision-bound review, and reach an existing participation route. A real human decision and any consequential execution remain separately authenticated and governed.

The ordered acceptance plan is `council-os/charter-completion-plan.json`. Completion receipts must name the actual source revision and test or receiving surface; this plan is not proof that a later release or appointment happened.

## Reuse the current infrastructure

Use Council OS and Public Watchdog for the canonical work register. Use the existing GitHub Discussions forum plus the email alternative for the first release. The native document tracker and portable tracker provide draft history, pinned sources and explicit editor/reviewer/decision states. The SQLite lab remains loopback-only feasibility evidence. Discourse is a later operating choice if the community needs and staffing justify another service.

The charter source register uses the canonical seven-group directory and document tracker. Each draft carries its register, charter and tracker digests, source ID, group document ID/version and public review route. Changing the register or tracker invalidates an earlier expected revision. No downloaded draft submits, approves or appoints anyone.

## One source, several projections

Run `python3 -B packages/charter-federation/build.py --root .`, then `node scripts/harness-x/render.mjs`. The latter emits the public charter register, static HF kit, offline Kaggle notebook and local MCP configuration. It refuses stale canonical inputs or generated package bytes. Do not hand-edit platform copies or register new live tools outside the existing capability workflow.

The public charter register and working-group tracker link to each other. Reading the source list works without JavaScript; local note and draft preparation require JavaScript. Notes stay in the browser and public downloads must contain only public or synthetic evidence.

## Verification and release

Run the package integrity/MCP/participation tests, exporter failure controls, notebook replay, native working-group tests and browser journeys. Check desktop/mobile, keyboard, no-JavaScript reading, storage failure and the source-to-group draft handoff. Preserve the original frozen root and legal-text recovery limitations. Automated checks do not establish representative-user or full accessibility acceptance.

Use protected master and the existing GitHub Actions release. Keep repository gates and the current production-writer convention intact. Verify the exact deployed files and the apex/Pages readback, then repeat the anti-clobber check. Platform publication requires a verified account/destination and its own byte/UI receipt; a candidate export is not a live deployment.

## Real operating work

The minimum human team is a consenting chair/deputy, competent reviewer, moderator, private-case owner and independent appeal reviewer. Record conflicts, terms, publication consent, retention, escalation and substitution. Provide assisted participation, language support, screen-reader testing and affected-user sessions. Do not turn researched prospects into appointed members or a typed name into verified human authority.

For the first trial, use the existing bounded revocation-latency project and synthetic/public evidence. Retain objections and unexpected outcomes. A model may explain or route a proposal; the human decision, final tool arguments and independent effect readback must meet the existing authority/Layer 0 contract. GSPC continues to use its sole canonical grader.
