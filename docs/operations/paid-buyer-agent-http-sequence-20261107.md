# Account-bound purchases over the existing MCP and HTTP doors

Codex. Draft source; autoMerge:false. Account-bound recovery is supported on the HTTP MCP full door. New purchase preparation requires the existing same-origin HTTP purchases API. This is not a claim of an MCP-only checkout, stdio caller authentication, production adoption or buyer acceptance.

1. Use a current Council session issued for the current account lifecycle. Send it as the HTTP Authorization Bearer header to the full /mcp door. Never place the token in tool arguments, URLs or payment payloads. The free /mcp/free door exposes no paid handler or private purchase context.
2. Call one of the existing five paid tools with its normal unpaid arguments. A PAYMENT_REQUIRED reply includes purchase_request: the exact underlying URL, resource, HTTP method and SHA-256 of its original request body. A challenge is not a settlement.
3. Before wallet approval, POST that exact purchase_request JSON to the same origin's /api/purchases/prepare with the same current Bearer header. Require csoai.purchase-preparation/1, exact request equality, and the returned owner hash, seed and request-bound nonce. Preparation creates no payment, output, receipt or acceptance.
4. The wallet owner may explicitly approve the advertised x402 authorization using that returned nonce. Include the non-secret csoaiPurchase sidecar with version:1 and the returned seed in the payment envelope. Keep the original tool arguments unchanged, send the envelope as x_payment on the same paid tool, and retain the transport Bearer header. The facilitator receives no Council token or sidecar. Never automatically sign or pay again after an uncertain response.
5. Read history with purchase_action:history on an existing paid tool. Recover one owned transaction with purchase_action:recover and purchase_transaction. Omit x_payment for recovery and all decision actions. Recovery returns original retained bytes and the stored route-reported receipt; it does not regenerate, call a provider, create a new signature or infer acceptance. Verify the original byte digest yourself. The route receipt remains unverified until separately checked.
6. Accept, reject or request correction only as an explicit buyer decision against the exact original digest/version and a stable request ID. If a decision write is unknown, reconcile that exact request with a read before considering any retry. An empty history page does not prove no payment occurred.

The focused purchase-http-isolation.test.ts controls enter the actual onRequest mount and real installed MCP SDK. They use synthetic lifecycle accounts, ephemeral authentication-only keys, in-memory stores and a single explicit synthetic unpaid route response. They exercise owner/wrong-owner/anonymous/lifecycle/free-door/concurrent-caller boundaries and the real HTTP preparation API. They make no real facilitator/provider/payment request and do not qualify a complete browser checkout or live Company case.
