# CHARTER — The Sovereign: One Portal, Three Scopes, Swappable Everything (2026-07-14)

Semantic charter for "the one the end user talks to." Extends CHARTER_OWEM_FOUR_SCOPE_SEMANTIC_MODEL.
Every claim here is either MEASURED (cite) or a design definition; nothing is a size/capability inflation.

## 1. WHAT THE END USER TALKS TO
Not a new model. **One Sovereign portal** — a single entrypoint (`sov33.py`, 100 capabilities) that routes a
request to whichever scope/brain fits. One face, many brains behind it. One identity, one care-floor (0.35),
one memory, one attestation chain. The user never picks a model; the Sovereign routes.

## 2. THREE SCOPES OF ONE SUBSTRATE (not four sizes, not a ladder to "sov5")
- **sov3**   — small scope: a person's character/companion (owem_world + memory_bridge), laptop-runnable.
- **sov33**  — medium scope: the tool/specialist layer (the capability MCP).
- **sov333** — large scope: governance + synthesis (gates + identity + T-scale base when hosted).
These are SCOPES OF ONE GOVERNED SUBSTRATE, not 3 separate products and not summable. There is no "sov5":
the unified thing is the PORTAL, not a bigger numbered model above sov333.

## 3. THE SWAPPABILITY PROPERTY (the strongest verified claim)
Any brain, any base model, any runtime is swappable while the SOVEREIGN GOVERNANCE stays constant.
- Governance DECOUPLED from body: `sov33_size_family.py` — governance hash unchanged across body depths
  (negative control catches a real side-effect). Governance is not a function of the model.
- Runtime swappable: `sov33_colibri_bridge.py` — SOV is an OpenAI-compatible client to Colibri / MLX / Ollama;
  swap the engine, keep the sovereign. The Venturi throat governs BEFORE the runtime.
- "The proof it works: change the model in the OWEM, the memory/identity/care-floor stay the same."

## 4. HONEST EMERGENCE DEFINITION (the word that must stay disciplined)
Routing 5 configs through a signed seam does NOT create a new mind or new capability. It creates a GOVERNED
DECISION that emerges from vote + care-gate. All raw capability comes from the base models; composing them
adds governance, routing, memory, attestation — NOT IQ. This is the Emergence ENGINE, not an emergent being.
Claiming otherwise is the exact category error Stage-7 AUDIT exists to catch.

## 5. BEST CONFIG — MEASURED, NOT DECLARED (equal-budget head-to-head, find_best_config_results.json)
Under EQUAL parameter budget (B=64, same task) the winner is ALLOCATION, not piece-count:
  1. 2-small+2-large large-heavy   0.0359   <- winner (concentrate budget in capable brains)
  2. single deep pyramid           0.0389
  3. 4-brain mean vote             0.0721
  4. 4-around-1 square             0.1123
  5. flat wide ensemble            0.1655
UNIFYING LAW (holds across every architecture run this session): add structure/pieces ONLY where residual or
regional structure exists to capture it; on a UNIFORM task, splitting a fixed budget across more brains LOSES
— concentrate it. 4-around-1 and multi-brain WIN when the task has regional structure (fractal-nest: nested
+59-60% at moderate region separation) and reliable routing; they LOSE under equal budget on a uniform task.
So "best config" is TASK-DEPENDENT: route by task structure, don't hard-wire one topology.

## 6. WHAT THIS MEANS FOR THE PORTAL
The Sovereign portal should ROUTE by task structure: uniform/simple -> concentrate budget (large brain);
regionally-structured -> the 4-around-1 / nested specialists. The router picking the right topology per task
IS the emergence engine's job. One portal, swappable brains, task-adaptive topology, constant governance.
