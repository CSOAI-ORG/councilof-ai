# 🍎 MLX / Apple-Silicon tuning — set up + measured (2026-07-14)
_Machine: Apple M4, 16 GB, 10-core, Metal available. Honest register: real numbers, real ceiling._

## What was NOT true before today
We had NOT done MLX tuning. All adapter/merge/RAG work ran on **CPU float32 PyTorch** (slow). MLX core was
present but unused; `mlx-lm` was not installed. (Ollama already used Metal for chat.)

## What's set up now (verified)
- **`mlx-lm` installed** in `~/.sovereign/ml-venv` — pure-Metal LLM run + train + quantize.
- **Metal confirmed** (`mx.metal.is_available() == True`).
- **4-bit quantization proven the real lever:**
  | Qwen3-0.6B | fp16 | 4-bit MLX |
  |---|---|---|
  | size | 1.4 GB | **331 MB** (4.2× smaller) |
  | speed | 10.7 tok/s | **28.3 tok/s** (2.6× faster) |

## Why this matters (the honest win)
4-bit cuts RAM ~4×, so **bigger models fit in 16 GB**: a 7B at 4-bit ≈ 4.5 GB fits; fp16 7B (14 GB) never would.
Realistic top on this Mac: **~a 4-bit 14B (~8 GB)**. Beyond that → free GPU. MLX does NOT raise the 16 GB ceiling;
it makes what fits smaller + faster, and makes on-device LoRA training fast.

## The commands (on-device workflow)
```bash
PY=~/.sovereign/ml-venv/bin/python
# 4-bit quantize any HF model to fit in 16GB:
$PY -m mlx_lm convert --hf-path Qwen/Qwen2.5-3B-Instruct --mlx-path ~/.sovereign/mlx_models/Qwen2.5-3B-4bit -q
# fast Metal inference:
$PY -m mlx_lm generate --model ~/.sovereign/mlx_models/Qwen2.5-3B-4bit --prompt "..."
# fast on-device LoRA training (replaces the slow CPU-PyTorch path):
$PY -m mlx_lm lora --model <mlx-model> --train --data <jsonl-dir> --iters 200
```

## Honest scope
- 16 GB RAM is the hard ceiling — unchanged. 4-bit just uses it ~4× more efficiently.
- For INFERENCE, Ollama (also Metal, quantized) is already comparable — MLX's edge is **training speed** + explicit **quantization control**.
- Artifact: `~/.sovereign/mlx_models/Qwen3-0.6B-4bit` (331 MB, working, 28 tok/s).
