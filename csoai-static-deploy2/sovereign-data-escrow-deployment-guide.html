Sovereign Data Escrow — Deployment Guide

1 UK-Only Infrastructure Provisioning (L0)

Deploy all storage and compute in UK data centres or on UK-sovereign hardware. No foreign cloud providers.

Requirements:

  • Physical residency: Data must be physically stored in UK territory. Acceptable: UK data centres, on-premise UK hardware, Apple Silicon MLX compute.
  • Provider attestation: Hosting provider must provide written confirmation of UK-only data residency. No "UK region" of a US provider (CLOUD Act exposure).
  • Network isolation: No direct peering with non-UK networks for Ring 0 data.
Verification: IP geolocation confirms UK. Provider contract includes UK-only clause. curl ifconfig.co/json returns country_code GB.

2 AES-256-GCM At-Rest Encryption with Per-Record DEK + Shamir KEK (L1)

Every data record gets its own Data Encryption Key (DEK). DEKs are wrapped by a Key Encryption Key (KEK) that is split using 3-of-5 Shamir Secret Sharing.

Configuration:

  • Per-record DEK: aes-256-gcm key generated per record using os.urandom(32).
  • Shamir KEK: Master KEK split into 5 shares with threshold 3. Shares distributed to: deploying organisation (2 shares), CSOAI (1 share), BFT council key custody (1 share), human-owner (1 share).
  • Key rotation: DEKs rotate every 90 days. KEK shares rotate annually.
  • No single point: Compromising any 2 of 5 shares does not expose data. Requires 3 of 5.
Verification: python -c "from escrow_mcp.crypto import verify_kek_shamir; verify_kek_shamir()" — PASS. Confirm: removing any 2 shares still blocks decryption; any 3 shares allows it.

3 TLS 1.3 mTLS for Internal Service Mesh (L2)

All inter-service communication uses mutual TLS (mTLS) with TLS 1.3. Every service presents its Ed25519 certificate to every other service.

Configuration:

  • TLS version: 1.3 only. TLS 1.2 disabled (except for specific legacy compatibility, BFT-approved).
  • mTLS: Both client and server present certificates. No one-way TLS.
  • Certificate authority: Internal CA (CSOAI sovereign CA) issues service certificates. No external CA dependency.
  • Cipher suites: TLS_AES_256_GCM_SHA384 only. All other suites disabled.
  • Certificate rotation: Every 30 days.
Verification: openssl s_client -connect escrow.internal:443 -tls1_3 — returns valid mTLS handshake. nmap --script ssl-enum-ciphers shows only TLS 1.3 / AES-256-GCM.

4 RFC3161 Trusted Timestamp Receipts (L4)

Every data access, modification, release, or destruction generates a timestamp receipt from an RFC3161 Trusted Timestamp Authority (TSA).

Configuration:

  • TSA: FreeTSA.org or organisational TSA. Receipt contains: data hash, timestamp, TSA signature.
  • Bitcoin OTS anchor: Every receipt is also anchored to the Bitcoin blockchain via OpenTimestamps for permanent tamper-evident proof.
  • Receipt storage: Receipts stored alongside the SIGIL ledger entry with permanent retention.
Verification: python -c "from escrow_mcp.timestamps import verify_all_receipts; verify_all_receipts()" — 507 receipts verified. Spot-check: 5 random receipts verified against TSA + Bitcoin OTS.

5 4-Eyes Release Gate Configuration (L5)

No single operator can release escrow data. Two authorised humans + one BFT witnessing agent are required.

Configuration:

  • Release approver 1: Named human operator (Ed25519 key registered).
  • Release approver 2: Named human supervisor (different Ed25519 key, different person).
  • BFT witness: One of the 33 BFT agents witnesses and co-signs the release.
  • Release workflow: Approver 1 initiates → Approver 2 co-signs → BFT agent witnesses → SIGIL receipt generated → data released.
  • Emergency override: In RC-5 (emergency) scenarios, 17/33 BFT quorum + human-owner can override to single-approver, with 24h post-hoc review.
Verification: Attempt single-approver release → BLOCKED. Attempt dual-approver without BFT witness → BLOCKED. Attempt dual-approver + BFT witness → SUCCESS with SIGIL receipt.

6 BFT Council Veto Configuration (L6)

The 33-agent BFT governance council can veto any data release at any stage.

Configuration:

  • Standard veto quorum: 23/33 agents must approve any standard release (RC-1, RC-3, RC-6).
  • Emergency quorum: 17/33 for emergency veto (RC-5).
  • Veto conditions: BFT agents are programmed to veto releases that: violate red lines, lack proper authorisation, have invalid timestamps, or show evidence of coercion.
  • Anti-collusion: Monitors detect coordinated voting patterns. Anomalous patterns trigger investigation.
Verification: Simulate release with 22/33 approval → BLOCKED (below quorum). Simulate with 23/33 → APPROVED. Simulate with 16/33 emergency → BLOCKED. Simulate with 17/33 emergency → APPROVED (RC-5 only).

7 SIGIL Audit Trail Activation

Every action in the escrow system generates a SIGIL receipt — the permanent, tamper-evident audit trail.

SIGIL Receipt Fields:
