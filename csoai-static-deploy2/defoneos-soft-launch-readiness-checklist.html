1. The release rule: evidence before enthusiasm

This checklist turns the DEFONEOS soft launch into a controlled release rather than a marketing assertion. A check is green only when a deterministic probe, a signed receipt, or an owner-confirmed action supports it. A page returning HTTP 200 is evidence that the edge serves bytes; it is not evidence that DSP registration, Cyber Essentials, SC clearance, or a grant application has been completed.

The public surface therefore separates three states: VERIFIED means the local artefact and live edge agree; OWNER-GATED means the next action requires Nick's personal information, signature, account, or send-button; DEFERRED means the capability is designed but deliberately not represented as operational; BLOCKED means a red-line or integrity condition prevents release. The soft launch can proceed with owner-gated commercial actions visible as gates, not hidden as achievements.

  • No external communication is sent by this checklist.
  • No defence certification, AUKUS partnership, or DEFONEOS-SEAL issuance is inferred from page publication.
  • No kinetic-targeting or personal-surveillance workflow is part of the public operator surface.

3. The five-stage soft-launch sequence

The release sequence is intentionally boring. First, freeze the intended page set and record local bytes. Second, deploy the static project and re-assign both custom aliases. Third, probe the canonical host, the new pages, the previous tick receipt, and the sitemap. Fourth, run the buyer walk-through using the evidence index. Fifth, publish only the verified surface and leave owner-gated actions as clearly labelled next steps.

A failed byte comparison is a release stop, not a cosmetic warning. A stale alias is treated as an edge integrity incident: keep the local artefacts, do not claim the pages live, and recover by re-deploying the static project before re-aliasing.

4. Deterministic smoke tests

The minimum smoke test is intentionally reproducible from a clean terminal. The canonical host is www.csoai.org; the apex may redirect. A successful probe records both the HTTP status and the body size, then compares the body size to the local file. This catches a stale Vercel alias, framework auto-detection, truncated writes, and stale tick receipts in one pass.

The launch operator should also inspect the first line of each page, verify the `<title>` and `meta description`, and confirm that the footer points to the sitemap and DEFONEOS home. These are human-readable checks, but they remain bounded by the byte-level release gate.

  • `curl -sL -o /dev/null -w '%{http_code}/%{size_download}' https://www.csoai.org/defoneos-soft-launch-readiness-checklist.html`
  • `curl -sL https://www.csoai.org/sitemap.xml | grep -c '<url>'`
  • `shasum -a 256 defoneos-soft-launch-readiness-checklist.html`
  • Probe at least one previous tick receipt after every alias change.

5. Governance and human authority

DEFONEOS uses a 33-seat BFT governance model for material system actions, while preserving a human-owner veto and a safe-state invariant. The page publication itself is not a DEFONEOS-SEAL issuance and does not constitute a council vote. The canonical review pattern for this sprint is 28 approve, 5 amend, 0 reject with quorum 25/33; that is a content review receipt, not a claim that every deployment decision has been externally certified.

Operational thresholds documented across the current substrate are 17/33 for an emergency proposal, 23/33 for a standard quorum, and 27/33 for a high-impact lockdown action. The threshold never authorises a prohibited action. No actor, agent, or page can override the immutable red lines.

7. Owner-gated actions are not silently automated

The soft-launch surface keeps the high-leverage commercial gates visible. DSP registration requires Nick's company and account details. Cyber Essentials requires the assessment path and payment or assessor interaction. SC clearance requires personal information. DASA, NATO DIANA and UKDI material is draft-ready but requires owner review and transmission. PyPI publication requires Nick's token. These are not technical failures; they are deliberate authority boundaries.

The correct public language is: materials are prepared, the owner action is identified, and no submission is represented as made. This keeps the page useful to a buyer without manufacturing a procurement history.

8. Rollback and recovery contract

A soft launch is only credible when it can be reversed without losing the evidence chain. The static project is deployed without the api/ directory so Vercel does not auto-detect a framework shell and serve the wrong response at page URLs. Each tick receipt records artefact names, byte counts, hashes, compliance alignment, red-line status and next actions. The previous receipt remains a probe target after the new alias is assigned.

If a page returns 404, the operator freezes claims, checks the alias target, verifies the deployment is ready, and re-runs the byte comparison. If the local directory is missing a claimed page, the page is recovered from the most recent verified edge deployment or the claim is reclassified. Nothing is deleted merely to make a counter look clean.

  • Preserve the current sitemap before mutation.
  • Use a static-only deployment root for this surface.
  • Record the deployment hostname in the final T110 SIGIL.
  • Do not announce the soft launch until the final SIGIL itself is live and byte-verified.

9. Buyer walk-through acceptance

A buyer should be able to answer four questions in under ten minutes: what does DEFONEOS do, where is the evidence, who can approve a material action, and what remains owner-gated? The evidence index provides the first two answers. The public operator handbook provides the third. This checklist and the explicit owner-gate table provide the fourth.

Acceptance is therefore behavioural, not theatrical. The buyer can inspect a live page, follow a cross-link, run a curl command, read the red-line boundary, and see a named next action. The absence of a claim is itself part of the assurance model.

10. The anti-patterns this checklist defeats

  • **No phantom page count.** Never turn a local filename into a live claim until the canonical edge returns matching bytes.
  • **No alias assumption.** A production deployment URL is not the same thing as www.csoai.org being pointed at it.
  • **No owner-gate laundering.** Drafts, prepared applications and templates are not submissions.
  • **No unsupported defence credential.** A public page is not a DEFONEOS-SEAL and does not imply DAIC certification or an AUKUS partnership.
  • **No red-line drift.** The public surface excludes kinetic targeting and personal surveillance patterns.
  • **No rollback amnesia.** Preserve receipts and reclassify honestly when local state and edge state diverge.
