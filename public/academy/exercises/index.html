Reproduce a published measurement

Each exercise re-runs one number or signature we publish, from the public bytes, and compares your result with ours. You finish an exercise when the two match and a deliberately broken copy fails.

Node 20 or later. No dependencies. The file you run is the same one this page runs.

Completion means reproduced

  • An exercise is complete only when it says REPRODUCED: the sha256 of your result equals the sha256 of the published result, and the negative control failed as it must.
  • Both results are written the same way before hashing: canonical JSON {"measurement": …, "value": …}, keys sorted, no whitespace.
  • Reading, watching or passing a quiz is not completion. Neither is a VALID from the published verifier on its own: that is a cross-check.
  • UNCHECKABLE means the check could not run (a network refusal, a browser without Ed25519). It is not a failure and not a completion.
  • Keep your transcript: both results, both digests, the control, and the sha256 of every input you read.

Read the living board and count it yourself

About 5 minutes · reads /api/gspc

How a published total is derived from the rows beneath it, and why slots and measurements are two numbers that are never added.

  1. Fetch /api/gspc.
  2. Count the rows of axes[] (slots) and the rows whose status is MEASURED (measurements).
  3. Compare your two counts with totals.axes and totals.measured_axes.
Expected
Your {axes, measured_axes} equals the board's own totals, byte for byte after canonicalisation.
Negative control
Change one MEASURED row to UNMEASURED and count again: the result must no longer match.
Live tools
GET /api/gspc · MCP board_totals
Complete when
State is REPRODUCED: your sha256 equals the published sha256 and the control failed.

Verify one signed measurement card with your own code

About 10 minutes · reads /.well-known/did.json, /signed/card_index.json, /signed/cards/<id>.json

Pin the key before trusting a signature; recompute the id from the canonical body; tell VALID, INVALID and UNCHECKABLE apart.

  1. Read the #card-attestation-1 key from /.well-known/did.json and pin it.
  2. Pick a card from /signed/card_index.json (default: the chain head) and fetch its card_url.
  3. Rebuild the preimage under Rule A (/signed/HOW-TO-VERIFY.md), check sha256(preimage) == id, then check the Ed25519 signature under the pinned key.
  4. Ask the published verifier (MCP verify_card) about the same card.
Expected
Your verdict for the card equals the verdict the published verifier returns for it.
Negative control
Append one character to a string in the body: your verifier must answer INVALID (id mismatch).
Live tools
GET /.well-known/did.json · GET /signed/card_index.json · GET /signed/cards/<id>.json · MCP verify_card
Complete when
State is REPRODUCED: your sha256 equals the published sha256 and the control failed.

Re-measure the whole signed card chain

About 15 minutes · reads /.well-known/did.json, /signed/card_index.json, /signed/cards/*.json, /api/state

A count published as 'measured' is a claim you can re-run: verify every card in the signed index and count the ones that verify.

  1. Run the verify-card check on every row of /signed/card_index.json.
  2. Count the VALID ones. A card you could not fetch is UNCHECKABLE, never INVALID.
  3. Compare your count with /api/state → card_chain.bodies_verified_valid.value.
Expected
Your count of VALID cards equals card_chain.bodies_verified_valid.value. This counts the signed card index only; never add it to another card corpus.
Negative control
Tamper one card body: your count must drop by one and no longer match.
Live tools
GET /signed/card_index.json · GET /signed/cards/<id>.json · GET /api/state

Prove a leaf is inside the public root

About 10 minutes · reads /root.json, /api/proof?sha=<leaf>

Recompute a Merkle root from one leaf and its audit path, and why the leaf count is part of the check.

  1. Fetch /root.json. Reject it unless card_sha256.length == card_count.
  2. Pick a leaf (default: a random one) and fetch its proof from /api/proof?sha=<leaf>. Reject the proof if index >= card_count.
  3. Walk the path: parent = sha256(left || right) over raw 32-byte digests; the index bit says which side you are on.
  4. Compare your root with root.json → merkle_root, and ask MCP verify_inclusion about the same leaf.
Expected
The root you recompute equals the published merkle_root.
Negative control
Flip the last hex digit of the leaf and walk the same path: the root must no longer match.
Live tools
GET /root.json · GET /api/proof?sha=<leaf> · MCP verify_inclusion
Complete when
State is REPRODUCED: your sha256 equals the published sha256 and the control failed.
node run-exercises.mjs --only inclusion

Check who signed the public root

About 10 minutes · reads https://csoai.org/.well-known/did.json, /.well-known/did.json, /root.json

Resolve a did:web identifier yourself and verify an Ed25519 signature over a stated preimage.

  1. Resolve did:web:csoai.org by fetching https://csoai.org/.well-known/did.json and read #board-attestation-1.
  2. Rebuild the preimage stated in root.json → sig_preimage: canonical JSON of {kind, schema, as_of, merkle_root, card_count, did_intended}.
  3. Verify root.json → sig_ed25519 under that key.
Expected
The signature verifies under the key the root names (did_intended).
Negative control
Add one to card_count in the preimage: the signature must no longer verify.

Keep the three card corpora apart

About 5 minutes · reads /root.json, /signed/card_index.json, /api/state

Three published card counts describe three different sets. Measure their overlap instead of adding them.

  1. Collect the public-root leaves (root.json → card_sha256) and the signed-index ids (card_index.json → cards[].card).
  2. Count the identifiers that appear in both sets.
  3. Compare with /api/state → signed_cards.corpus_relation.
Expected
Your {relationship, identifier_overlap, public_root_leaves, separately_indexed_signed_cards} equals the published corpus_relation. The two sizes are never added.
Negative control
Copy one signed-index id into the root set: the overlap must become 1 and no longer match.

Verify the board snapshot stamp

About 10 minutes · reads /api/gspc, /.well-known/did.json

A signature over a whole payload: remove the stamp, canonicalise what is left under the stated rule, verify under the named key.

  1. Fetch /api/gspc and set site_attestation aside.
  2. Canonicalise the rest under the rule in site_attestation.sig_input (keys sorted, no whitespace, non-ASCII literal, ECMAScript numbers).
  3. Verify site_attestation.sig under #board-attestation-1 from /.well-known/did.json.
Expected
The stamp verifies. It attests the integrity of the snapshot as served, not a re-measurement.
Negative control
Change one axis row's status before canonicalising: the stamp must no longer verify.
Live tools
GET /api/gspc · GET /.well-known/did.json
Complete when
State is REPRODUCED: your sha256 equals the published sha256 and the control failed.
