x402 Buyer Guide

How to pay for Council of AI evidence artefacts using x402 (USDC on Base). For agent developers and platform integrators.

The 30-second version

# 1. GET a paid resource → 402 with payment challenge
curl -i "https://councilof.ai/api/request-attestation?subject=USDC"
# → HTTP/1.1 402 Payment Required
# Read accepts[] in the JSON body for amount, network, asset and payTo.
# The v2 PAYMENT-REQUIRED header contains the base64-encoded challenge.

# 2. Use an x402 client to create the signed payment payload for these terms.
# 3. Retry the same resource with the v2 PAYMENT-SIGNATURE header.
curl -H "PAYMENT-SIGNATURE: <base64-encoded-payment-payload>" \
     "https://councilof.ai/api/request-attestation?subject=USDC"
# → HTTP 200 + paid artefact only after verified settlement

The placeholder is a signed x402 payment payload, not a transaction hash or an offer-receipt JWS. Legacy v1 clients use X-PAYMENT. Read the current amount from the challenge, including any active promotion; a 402 is an offer, not proof of payment.

Verification — always free

# Browse the public root and fetch a card named by that root.
curl "https://councilof.ai/root.json"
curl "https://councilof.ai/cards/<sha16-from-root>.json"

# Verify an x402 offer or receipt JWS with the repository verifier.
# Requires Python's cryptography package; fetches the public DID document.
python3 scripts/verify_receipt.py --jws '<receipt.jws>'
# Or send a JSON object to the hosted verifier.
curl "https://councilof.ai/api/receipts/verify" \
     -H 'Content-Type: application/json' \
     -d '{"receipt":"<receipt.jws>"}'

For measurement-card signatures and their verification rules, use the free card verifier. A valid signature proves signed bytes; settlement and measurement claims have their own evidence.

Common patterns

"I want the current measurement board without a wallet"

curl "https://councilof.ai/api/gspc"
curl "https://councilof.ai/api/cards"

"I want a signed receipt for my compliance dossier"

# Paid: settle the 402 challenge (USDC on Base)
curl "https://councilof.ai/api/request-attestation?subject=USDC"
# Create the signed payment payload, then retry with PAYMENT-SIGNATURE.

"I need an EU AI Act Article 50 evidence bundle"

# First inspect the free preview for your exact subject.
curl "https://councilof.ai/api/evidence-bundle?obligation=article-50&subject=model-id"
# Paid: use the same subject and add bundle=1 to request the 402.
curl "https://councilof.ai/api/evidence-bundle?obligation=article-50&subject=model-id&bundle=1"

Replace model-id with the subject you need. Check relevant_signed_cards before paying: zero means the selection is empty, and payment creates no new measurements.

Before ordering, inspect the native record family and limits of each selected card. relevant_signed_cards counts records, not independent measurements. Provider-page byte-change notices report a change in observed bytes; their meaning, cause and materiality require separate evidence. Marking-census notices that report no detector or sample probes do not establish fresh marking-test results. Different wrappers may contain equal payloads; retain their distinct identities. Assembly reuses existing records and does not verify input-card signatures. Check the selected records and applicable attribution and notices, and review payment and delivery terms before ordering.

"I want to prove this card is in your canonical Merkle root"

# One leaf: free
curl "https://councilof.ai/api/proof?sha=<64-hex>"
# Multiple leaves: paid batch (settle the 402)
curl "https://councilof.ai/api/proof?bundle=1"

"I need a verifiable historical measurement batch"

receipts_batch assembles selected, already-published card-v0 measurement leaves and their available inclusion evidence for your review window. It does not run new measurements or provide payment receipts. Preview and verification are free.

  1. Fix the scope and preview it. For this recipe, set both from and to to explicit UTC ISO-8601 instants ending in Z, using whole seconds or at most three fractional digits; the bounds are inclusive. Use the exact returned window and buy.resource for replay. Nonzero milliseconds are preserved; exact whole seconds retain their whole-second form. Do not silently round your requested bounds. Save the returned window, count, matched, cap, truncated, next_from, span, sources, batch_sha256 and batch_bytes. Decide whether the selected leaves answer your review question before paying. 
    # Historical example; replace both dates with your review window.
curl "https://councilof.ai/api/receipts/batch?from=2026-10-01T00:00:00Z&to=2026-10-09T00:00:00Z&preview=1"
# MCP equivalent: receipts_batch({from, to, preview: true})

    The cap is 200 leaves per batch. Counts describe the current published inputs, not every measurement ever made. If truncated is true, this is partial coverage. A next_from timestamp can overlap the previous batch: deduplicate by leaf sha256 and check that the cursor advances. If it does not advance, or same-time leaves prevent complete coverage, keep coverage unresolved and use the existing enquiry route.

  2. Read fresh terms, then choose whether to pay. Request the same window without preview=1. Use the fresh 402 accepts[] terms and verify its offer JWS as described above. Confirm csoai.preview.batch_sha256 still matches your saved preview; the published inputs can change. The offer JWS commits payment terms and the resource URL, not the batch digest. Use your own compatible x402 client and wallet to authorize payment and retry the same resource. In HTTP use the challenge's supported payment header; in MCP pass the payment payload as x_payment. Save the settlement result separately from the delivered artifact.
  3. Check the delivered bytes and evidence. Continue these artifact checks only after a delivered 200 response. A returned unsigned manifest is an output with signature unmeasured; inspect manifest_card.sig_ed25519 and unsigned_reason. A PAID_NOT_DELIVERED signing-error response contains no delivered batch or manifest: preserve the settlement receipt and reconcile with CSOAI before any reissue; do not automatically retry or pay again. Save the complete delivered response. Hash response.batch using the canonicalization below, then require that digest to equal your saved preview, response.batch_sha256 and response.manifest_card.payload.batch_sha256. Require the canonical byte length to equal manifest_card.payload.batch_bytes and your saved preview. Do not hash the outer response or pretty-printed JSON. 
    // Same recursive key ordering as the published cardSign canonicalizer.
const ordered = v => Array.isArray(v) ? v.map(ordered)
  : v && typeof v === "object"
    ? Object.fromEntries(Object.keys(v).sort().map(k => [k, ordered(v[k])]))
    : v;
const bytes = new TextEncoder().encode(JSON.stringify(ordered(response.batch)));
const digest = [...new Uint8Array(await crypto.subtle.digest("SHA-256", bytes))]
  .map(b => b.toString(16).padStart(2, "0")).join("");

    Separately verify the manifest and each included card signature under your expected signer policy, and fold each leaf's proof against its carrying root using the published root-verification instructions. A digest match proves byte consistency; it does not prove signatures, root inclusion, or the truth of a measurement. A returned unsigned manifest leaves its signature unmeasured; an unavailable root stays unresolved, and a failed verification remains invalid under the applicable check. Manifest root inclusion can remain unmeasured.

  4. Record acceptance and a real next use. The reviewer records whether the verified leaves answer the agreed question, with the accepted batch digest, window, coverage limits and an attributable acknowledgement. Preserve the linked settlement and delivery evidence; payment alone is not acceptance. For a later review, repeat with a second actual window and retain a second delivery and acceptance record. Operator checks of the preview or verifier are QA, not outside-user use or revenue.

MCP integration

Connect a Streamable HTTP MCP client to https://councilof.ai/mcp. Use tools/list for its current tool definitions; the discovery manifest also lists free and paid tools. Paid tools use the same x402 rail.

What we never sell:
  • A score, rank, or grade
  • A certificate of compliance
  • A MEASURED cell (payment mints no new measurement)
  • A conformity determination
  • Private data (every payment uses already-public cards)
