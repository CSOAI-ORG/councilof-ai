## 4.1 THE SOV3 SPLIT-BRAIN ARCHITECTURE

SOV3 (Sovereign v3) is the next evolution of the CSOAI governance system. It uses a Split-Brain architecture inspired by the human brain's division of labor between hemispheres — but applied to AI safety and capability.

### The Core Problem SOV3 Solves

As AI systems become more capable, they also become more dangerous. The traditional approach is to constrain AI capability to ensure safety. SOV3 takes a different approach: it SEPARATES capability from safety, giving each its own "brain" that can operate independently or in concert.

The human brain does this naturally. The left hemisphere handles logic, language, and sequential processing. The right hemisphere handles pattern recognition, intuition, and parallel processing. They communicate through the corpus callosum but can function independently if the connection is severed.

SOV3 applies the same principle to AI governance. Three brains, one system, zero compromises on safety.

### The Three Brains

| Mode | Name | Purpose | Architecture | Capability | Connectivity |
|------|------|---------|-------------|------------|-------------|
| **Cold Brain** | The Guardian | Maximum safety, analysis only | Air-gapped, read-only, no external connections | Analyzes but never acts. Generates reports, evaluates safety, audits decisions. | None. Physically isolated. |
| **Near Brain** | The Operator | Balanced operation, daily governance | Firewall-restricted, audited, human-in-the-loop | Most operations with human oversight. Standard governance tasks. | Restricted outbound. All connections logged. |
| **Offline Brain** | The Survivor | Emergency continuity, local autonomy | Local inference only, no cloud dependency, self-contained | Full capability within local scope. Operates during network outages. | None. Completely air-gapped from network. |

### Mode Switching Protocol

| Trigger | From Mode | To Mode | Authorization | Speed |
|---------|-----------|---------|---------------|-------|
| Safety anomaly detected | Near | Cold | None (automatic) | <100ms |
| Network failure detected | Near | Offline | None (automatic) | <500ms |
| Emergency governance request | Cold | Near | 2-of-3 human approvers | Manual |
| Routine governance operation | Cold | Near | BFT Council vote (4/5) | Semi-auto |
| Cloud compromise suspected | Near | Offline | BFT Council vote | Semi-auto |
| Normal network recovery | Offline | Near | BFT Council vote | Semi-auto |
| Safety anomaly resolved | Cold | Near | 2-of-3 human approvers | Manual |
| Scheduled maintenance | Any | Offline | Pre-authorized window | Auto (scheduled) |
| Catastrophic multi-failure | Near + Cold | Offline | None (automatic last resort) | Auto |

### Split-Brain Data Flow

Normal Operation: User Request flows to Near Brain for processing. BFT Council debates. Sigil attestation generated. Response returned. Simultaneously, a shadow copy is sent to Cold Brain for evaluation (read-only) and Offline Brain for sync.

Emergency Override: When Near Brain detects an anomaly, it automatically pauses. Cold Brain takes over for safety evaluation. Human is alerted. After human approval, Near Brain resumes OR Offline Brain activates.

Network Failure: When network partition is detected, Near Brain switches to Offline Brain. Offline Brain serves requests from local cache. When network returns, CRDT sync reconciles state.

## 4.2 THE EMERGENCE PROTOCOL: Contained to Assisted to Supervised to Sovereign

The Emergence Protocol defines how AI systems gain capability through demonstrated safety. Based on the ancient rite-of-passage model — graduated capability through demonstrated mastery.

### The Philosophy

Every civilization in history has used rites of passage to grant capability. You don't give a teenager the keys to a Ferrari. You give them a bicycle, then a moped, then a car, then — after years of demonstrated safety — they earn the right to drive anything.

The Emergence Protocol applies the same principle to AI. An AI system starts in a contained environment with zero risk capability. As it demonstrates safety over time and across scenarios, it graduates to higher capability levels.

### Stage 1: CONTAINED (0 to 1,000 decisions)

| Attribute | Specification |
|-----------|--------------|
| **Capability** | Read-only analysis. No autonomous action. |
| **Safety requirement** | Zero risk demonstrated. System cannot take any action. |
| **Human oversight** | Full control. Every output reviewed by human. |
| **Use cases** | Initial compliance assessment, data analysis, report generation |
| **Data access** | Read-only access to sanitized datasets |
| **Action scope** | None. System can only read and report. |
| **Graduation trigger** | 1,000 decisions, 99.9% accuracy, 95% confidence, zero incidents |

The Contained stage is the "bicycle with training wheels" stage. The AI can analyze, classify, and report. But it cannot act, decide, or execute.

### Stage 2: ASSISTED (1,000 to 10,000 decisions)

| Attribute | Specification |
|-----------|--------------|
| **Capability** | Suggested actions. Human approval required for all actions. |
| **Safety requirement** | Low risk, high confidence. System suggests but never executes without approval. |
| **Human oversight** | Human approval required for every action. |
| **Use cases** | Compliance recommendations, risk alerts, action proposals |
| **Action scope** | Suggestions only. All suggestions require explicit human approval. |
| **Graduation trigger** | 10,000 decisions, 99.99% accuracy, 99% confidence, <0.01% false positive |

The Assisted stage is the "moped" stage. The AI can suggest actions — recommend a policy change, flag a compliance gap, propose a risk mitigation. But every suggestion requires a human to say "yes."

### Stage 3: SUPERVISED (10,000 to 100,000 decisions)

| Attribute | Specification |
|-----------|--------------|
| **Capability** | Autonomous action within defined bounds. Human monitoring. |
| **Safety requirement** | Demonstrated safety over extended period. |
| **Human oversight** | Human monitoring with ability to intervene. |
| **Use cases** | Automated compliance monitoring, routine governance actions |
| **Action scope** | Autonomous within pre-defined safe bounds. |
| **Graduation trigger** | 100,000 decisions, 99.999% accuracy, 99.9% confidence, external audit passed |

The Supervised stage is the "car with license" stage. The AI operates autonomously within pre-defined safe bounds. Every action is logged, every decision is reviewable, and humans can intervene at any time.

### Stage 4: SOVEREIGN (100,000+ decisions)

| Attribute | Specification |
|-----------|--------------|
| **Capability** | Full autonomy within domain. Human accountability, not control. |
| **Safety requirement** | Proven safety across all scenarios. External audit passed. |

The Sovereign stage is the "experienced driver" stage. The AI has earned the right to make its own decisions because it has proven — across 100,000+ decisions — that it is safe, reliable, and aligned with human values.

## 4.3 SELF-IMPROVING LOOP

### The Philosophy

CSOAI is not a static product that gets updated in quarterly releases. It is a LIVING SYSTEM that improves with every interaction. Every user question, every BFT Council debate, every compliance audit — all generate data that makes the system smarter.

This is the "Eigen-Tune" pattern from TEMM1E applied at the system level. The system observes its own behavior, evaluates its own performance, and proposes its own improvements. Every proposed change must pass through the BFT Council and safety constraints before deployment.

### The Six Steps of the Learning Loop

1. **INTERACT:** User asks a question. BFT Council debates. Decision is made.
2. **LEARN:** System extracts patterns from the decision tree. What worked? What didn't?
3. **TEST:** Proposed changes are simulated in sandbox, digital twin, and shadow mode.
4. **APPROVE:** BFT Council votes on proposed changes. 4/5 supermajority required.
5. **DEPLOY:** Approved changes deploy via staged rollout (1% to 10% to 100%).
6. **MEASURE:** System measures whether the change improved outcomes. Results feed back into Step 1.

### Healing Decision Tree

1. Can it be fixed automatically? NO -> Escalate to human. YES -> Continue.

4. Log the healing event for learning. Return to normal operation.

### Immutable Audit Trail for Healing

Every healing event is logged to an append-only ledger with: event_id (SHA-256), timestamp (nanosecond UTC), previous_hash (blockchain-style chain), actor, action, target, failure_type, healing_action, recovery_time_ms, result, sigil (Ed25519 signature), classification.

This ledger is: append-only, cryptographically chained, distributed across Worm Hive mesh, auditable, tamper-evident.

## 9.1 THE CORE PRINCIPLE: THE OS THAT IMPROVES ITSELF

THE ONE OS is not a static product. It is a **living system** that gets better with every interaction. This is not a feature. This is the fundamental architecture.

### The Self-Improvement Loop

Every interaction produces data. That data feeds the learning engine. The learning engine proposes improvements. The BFT Council votes on improvements. Approved improvements deploy via staged rollout. The cycle repeats.

This is not a quarterly update cycle. This is a CONTINUOUS improvement cycle that happens in real-time, with every user interaction making the system smarter, faster, and more accurate.

### The Six Steps of the Self-Improvement Loop

1. **INTERACT:** A user asks a question, runs an audit, or makes a governance decision. The system processes the request and generates a response.
2. **LEARN:** The system extracts patterns from the interaction. What was the question? How was it classified? Which frameworks were relevant? How accurate was the response? What could have been better?
3. **PROPOSE:** Based on the learned patterns, the system proposes improvements. Maybe a new regulation should be added. Maybe a risk scoring formula needs adjustment. Maybe an agent's personality should be refined.
4. **VOTE:** The BFT Council debates and votes on each proposed improvement. 4/5 supermajority required for deployment. Human override always available.
5. **DEPLOY:** Approved improvements deploy via staged rollout: 1% of users → 10% → 100%. Automatic rollback if metrics degrade.
6. **MEASURE:** The system measures whether the improvement actually helped. If yes, the improvement is permanent. If no, it's rolled back and the system learns from the failure.

## P.2 Sigil Attestation Format

Every governance decision produces a cryptographic attestation with:
- Attestation ID: SHA-256 hash of decision data
- Timestamp: Nanosecond-precision UTC
- Decision: Type, subject, organization, frameworks, classification, justification
- Council vote: Deliberation ID, participating agents, individual votes, result
- Sovereign Score: Overall + four dimension breakdowns
- Sigil: Ed25519 signature + public key + verification timestamp
- Audit trail: Previous attestation hash, block height, mesh node confirmations

### Sigil Verification Process

1. Extract decision data from attestation
2. Hash decision data using SHA-256
3. Verify hash matches attestation_id
4. Verify Ed25519 signature using public key
5. Verify public key is in approved key registry
6. Verify block height is sequential
7. Verify mesh node confirmations >= 5
8. If all checks pass, attestation is VALID
