1. libp2p for AI Agents
1.1 What is libp2p?
libp2p is a modular peer-to-peer networking stack developed by Protocol Labs. It is the networking layer that powers IPFS (InterPlanetary File System), Ethereum 2.0, Filecoin, Polkadot, and over 30 major blockchain and distributed systems, collectively securing and moving over $100B in value across the open internet.
“For nearly a decade, libp2p has defined secure, modular, and high-performance peer-to-peer networking… evolving from a widely adopted networking library into foundational infrastructure for internet-scale, decentralized systems.” – libp2p 2025 Annual Report
Key Characteristics: - Modular: Transport, security, multiplexing, and discovery are swappable components - Multi-language: Implementations in Go, Rust, JavaScript, Python, Java, Nim, C++ - Transport-agnostic: Works over TCP, QUIC, WebRTC, WebSocket, WebTransport - Battle-tested: Powers production networks with millions of nodes - NAT-traversal built-in: 70%+ direct connection success rate via DCUtR - Cryptographically secure: Noise and TLS 1.3 for all connections

1.3 Key Protocols for Agent Networks
1.3.1 Identify Protocol (/ipfs/id/1.0.0)
The Identify protocol exchanges keys and listen addresses between peers. When two agents connect, they automatically share: - Their PeerID (public key hash) - Their listen addresses (where they accept connections) - Their observed addresses (what the remote peer sees) - Their supported protocols (what application protocols they speak)
Why it matters for agents: Agents automatically learn each other’s capabilities and addressing information without manual configuration.
1.3.2 Ping Protocol (/ipfs/ping/1.0.0)
A simple keepalive mechanism. Peers periodically ping each other to verify connectivity and measure latency.
Why it matters for agents: Agents can detect when peers go offline, measure network health, and make routing decisions based on latency.
1.3.3 Kademlia DHT (/ipfs/kad/1.0.0)
The Kademlia Distributed Hash Table is a decentralized key-value store that enables: - Peer routing: Find an agent by its PeerID - Content routing: Find agents that provide specific content/services - Value storage: Store and retrieve signed records
Key parameters: - k = 20: Each bucket holds up to 20 peers - alpha = 10: Concurrency factor for lookups - XOR distance metric: distance(A, B) = A XOR B - O(log n) lookup complexity
Routing Table Structure:
Bucket 0: Nodes at distance 2^0  to 2^1-1   (1 bit shared prefix)
Bucket 1: Nodes at distance 2^1  to 2^2-1   (2 bits shared prefix)
Bucket 2: Nodes at distance 2^2  to 2^3-1   (3 bits shared prefix)
...
Bucket n: Nodes at distance 2^n  to 2^(n+1)-1
1.3.4 GossipSub (/meshsub/1.1.0, /meshsub/1.2.0, /meshsub/2.0.0)
GossipSub is the publish-subscribe protocol used by agents to broadcast messages. It combines: - Mesh formation: Each peer maintains a set of mesh neighbors per topic - Gossip: Peers gossip about message metadata (IHAVE) to random peers - Pruning/Grafting: Dynamic mesh maintenance based on peer scores - Peer scoring: Behavior-based scoring to detect and isolate malicious peers
GossipSub v1.1 Security Extensions: - Peer Scoring: 7 parameters (P1-P7) track peer behavior - Flood Publishing: Messages published to all scored peers (not just mesh) - Opportunistic Grafting: Escapes from sybil-poisoned meshes - Explicit Peering Agreements: Direct connections between trusted peers - Spam Protection: IHAVE/IWANT limits, graylisting
GossipSub v2.0 (2025): - Lazy-pull mechanism: IANNOUNCE/INEED control messages - Near-zero duplicate messages - Doubles blob count capacity for Ethereum - Enhanced peer scoring with P6 (IP colocation) and P7 (behavioral penalties)
1.3.5 Circuit Relay v2 (/libp2p/circuit/relay/0.2.0)
Circuit Relay enables peers behind NAT/firewall to communicate through intermediate relay nodes: - Reservation: NATed peer reserves a slot on a public relay - Relayed connection: Other peers connect via the relay - Multi-hop prevention: Relay chaining is blocked for security - Signed peer records: Secure relay-peer binding
Two relay roles: - Hop: Relays traffic between peers (public nodes) - Stop: Originates or terminates relayed traffic (any peer)
1.3.6 DCUtR: Direct Connection Upgrade through Relay (/libp2p/dcutr)
DCUtR is the NAT traversal protocol that upgrades relayed connections to direct connections via hole punching:
┌─────────┐                    ┌──────────┐                    ┌─────────┐
│ Agent A │───Relayed Conn───▶│  Relay   │◀───Relayed Conn───│ Agent B │
│ (NATed) │                    │ (Public) │                    │ (NATed) │
└────┬────┘                    └──────────┘                    └────┬────┘
     │                                                              │
     │  1. A learns B's public address via relay (IDENTIFY)         │
     │  2. B learns A's public address via relay (IDENTIFY)         │
     │  3. Both synchronize using RTT measurements                  │
     │  4. Both send simultaneous CONNECT packets                   │
     │  5. NATs create mappings → Direct connection established!    │
     │◀══════════════════════ Direct Path ══════════════════════════▶│
     │           (Relay connection can now be closed)               │
Large-Scale DCUtR Performance (2025 Study - 4.4M attempts, 85K+ networks, 167 countries):
End-to-end connectivity: The unconditional success rate (including relay reservation failures) is ~50%, as ~29% of attempts fail at prerequisite stages.
1.3.7 AutoNAT
AutoNAT detects a peer’s NAT status by asking other peers to attempt dialing back. This enables: - Self-awareness of NAT type - Automatic relay reservation when behind NAT - Connection reversal optimization when publicly reachable
1.3.8 mDNS (/ipfs/mdns/1.0.0)
Multicast DNS enables peer discovery on local networks without any infrastructure: - Broadcasts peer presence on local subnet - Zero configuration - Works for agents on the same LAN
1.3.9 Rendezvous Protocol (/libp2p/rendezvous/1.0.0)
The Rendezvous protocol enables peers to discover each other based on shared strings (“rendezvous points”): - Peer registers with a rendezvous string on a rendezvous server - Other peers query for the same string - Enables topic-based discovery without a DHT

2.2 DHT-Based Agent Discovery (Global Scale)
The Kademlia DHT is the primary mechanism for global agent discovery:
Agent Advertisement: 1. An agent computes the DHT key for its capability (e.g., sha256("capability:image_generation")) 2. The agent performs PUT_VALUE(key, agent_record) to store a signed record at the k closest nodes 3. The record contains: PeerID, multiaddrs, capability list, expiration timestamp, signature
Agent Lookup: 1. An agent seeking a capability computes the same DHT key 2. It performs GET_VALUE(key) which routes to the k closest nodes 3. Returns the stored agent records with addresses and capabilities
Provider Records: - ADD_PROVIDER(content_hash): An agent advertises it has specific content/skills - GET_PROVIDERS(content_hash): Find agents that can provide specific services
2.3 mDNS for Local Agent Discovery
mDNS (multicast DNS) enables zero-configuration discovery on local networks:
How it works: 1. Each agent broadcasts its PeerID and multiaddrs via multicast on the local subnet 2. Other agents on the same network receive these broadcasts 3. No central server, no configuration required 4. Typical discovery period: 10-20 seconds
Best for: Agents running in the same datacenter, office, or home network.
2.4 Rendezvous Protocols for Agents Behind NAT
The Rendezvous protocol enables topic-based discovery:
An agent registers on a rendezvous point with a string like "capability:nlp/v1"
Searching agents discover peers registered under the same string
The rendezvous server returns PeerIDs and multiaddrs
Agents can then connect directly via the DHT
Rendezvous vs DHT: - DHT: Decentralized, global, slower, no single point of failure - Rendezvous: Faster, topic-organized, requires rendezvous servers
2.5 Gossip Protocols for Agent Status Broadcasting
GossipSub enables agents to broadcast status and availability:
Topic Structure:
/agents/status          -- Agent heartbeat/status updates
/agents/capabilities    -- Capability advertisements  
/agents/tasks           -- Task availability and bidding
/agents/reputation      -- Reputation score updates
How agents spread status: 1. Each agent subscribes to relevant topics 2. GossipSub forms a mesh of ~6 peers per topic 3. Status messages are published to the mesh 4. Each peer gossips message metadata (IHAVE) to random peers 5. Messages propagate through the network in O(log n) hops 6. Missing messages are requested via IWANT
GossipSub v2.0 Lazy-Pull: - IANNOUNCE: Broadcast only message IDs (not full messages) - INEED: Request specific messages from peers - Reduces bandwidth by ~50% with minimal latency impact
2.6 How 47 Agents Maintain Connectivity in a Mesh
With 47 agents, the mesh is small enough for efficient operation:
Connection Strategy: - Each agent maintains D = 6 mesh peers per subscribed topic (GossipSub default) - Direct connections to known/collaborating agents (explicit peering) - DHT routing table contains ~20-40 peers (k-buckets fill quickly) - All connections secured with Noise protocol
Discovery Flow for 47-Agent Network: 1. New agent joins with bootstrap list (3-5 known agents) 2. DHT lookups populate routing table within seconds 3. GossipSub PX (peer exchange) discovers additional mesh peers 4. mDNS discovers agents on same LAN automatically 5. Within ~30 seconds, agent has full network awareness
Path Diversity: - Average path length in 47-node Kademlia: ~2-3 hops - Mesh overlay provides multiple redundant paths - Direct connections preferred (via DCUtR when NATed)

3. Agent Identity on P2P Networks
3.1 PeerID (libp2p) vs Ed25519 Sigil (CSOAI)
libp2p PeerID: - Derived from the hash of the agent’s public key - Default: Ed25519 keypair → SHA-256 hash → multibase encoding - Example: 12D3KooWC5c39mad27di37ubxUymmoohVhWNedMbPrUzYN7tiV2R - Self-certifying: The PeerID proves ownership of the private key - Used for: network addressing, routing table keys, connection security
Ed25519 Sigil (CSOAI): - A higher-level identity construct built on top of libp2p PeerID - Contains: Ed25519 public key, metadata, revocation info, human-readable name - Bound to the PeerID but carries additional agent-specific attributes - Enables: human-readable names, capability attestations, reputation linkage

3.2 Cryptographically Proving Agent Identity
At Connection Time (libp2p): 1. Agent A initiates connection to Agent B 2. Noise protocol handshake includes PeerID authentication 3. Both sides prove possession of private key corresponding to PeerID 4. Man-in-the-middle impossible without breaking Ed25519
At Application Time (ratify-protocol): 1. Agent presents a ProofBundle: delegation chain + fresh challenge signature 2. Verifier checks: cert validity, signature, revocation status, scope intersection 3. Stateless verification – no central service required on the hot path 4. Challenge freshness (<=300s window) prevents replay attacks
DIAP (Decentralized Agent Identity Protocol) Approach: 1. Agent generates Ed25519 keypair → derives did:key identifier 2. Creates DIDDocument with public key and encrypted P2P endpoint 3. Publishes to IPFS → gets immutable CID 4. Proves ownership via Zero-Knowledge Proof (ZKP) 5. CID + ZKP = stateless, offline-verifiable identity
3.3 ratify-protocol: Quantum-Safe Agent Identity
ratify-protocol (by Identities AI) is a cryptographic trust protocol for human-agent and agent-agent interactions.
Key Features: - Hybrid cryptography: Ed25519 + ML-DSA-65 (FIPS 204) – both signatures required - Quantum-safe: ML-DSA-65 is lattice-based, resistant to Shor’s algorithm - Stateless verification: No round-trip to central service on the hot path - Delegation chains: HumanRoot → Agent → Sub-agent with scope narrowing - Revocation: Signed revocation lists with real-time push propagation - Key rotation: Cryptographic continuity when keys change

3.4 Revocation: What Happens When an Agent is Compromised?
Revocation Mechanism: 1. Principal (human or delegating agent) publishes a signed RevocationList 2. List contains cert IDs that are revoked 3. Verifiers check revocation before accepting any ProofBundle 4. RevocationPush: Real-time propagation to verifiers (staleness in milliseconds) 5. ForceRevocationCheck: High-stakes endpoints can force fresh revocation checks

3.5 Key Rotation for Long-Running Agents
Challenge: Agents may run for months or years. Keys may need rotation due to: - Suspected compromise - Organizational policy - Quantum migration - Scheduled rotation
Rotation Protocol: 1. Generate new Ed25519 + ML-DSA-65 keypair 2. Create KeyRotationStatement signed by BOTH old and new keys 3. Publish to DHT (replaces old record) 4. Update all delegation certs to point to new key 5. Old key’s delegations are valid for a grace period, then revoked 6. Peers update their peerstore with the new key

4.2 Request/Response (Like HTTP but P2P)
The fundamental pattern: Agent A opens a stream to Agent B, sends a request, receives a response.
// Agent A sends a task request to Agent B
stream, _ := host.NewStream(ctx, peerID, "/agent/task/1.0.0")
request := TaskRequest{
    TaskID:   "task-123",
    Type:     "image_generation",
    Prompt:   "A futuristic city",
    Budget:   "0.5 SEI",
    Deadline: time.Now().Add(5 * time.Minute),
}
json.NewEncoder(stream).Encode(request)

// Agent B processes and responds
var response TaskResponse
json.NewDecoder(stream).Decode(&response)
// response: {Accepted: true, Price: "0.5 SEI", ETA: "30s"}
Best for: Task assignment, capability queries, one-off interactions.
4.3 Publish/Subscribe (Like Kafka but P2P)
Agents subscribe to topics and receive all messages published to those topics.
// Subscribe to a capability topic
await node.services.pubsub.subscribe('agents/capabilities/nlp')

// Publish availability
await node.services.pubsub.publish(
  'agents/capabilities/nlp',
  new TextEncoder().encode(JSON.stringify({
    peerId: node.peerId.toString(),
    capability: 'text_summarization',
    load: 0.3,
    available: true
  }))
)
Best for: Status broadcasting, availability announcements, event distribution.
4.4 Gossip (Status Updates Spread Virally)
GossipSub’s gossip mechanism spreads metadata about messages even to peers not in the mesh.
How it works: 1. A peer randomly selects ~3 peers per heartbeat (1 second) 2. Sends IHAVE: “I have messages [id1, id2, id3]” 3. Peer that missed a message sends IWANT: “I want message id2” 4. Original peer sends the full message 5. Message spreads virally through the network
Best for: Reputation score propagation, lightweight status updates.
4.5 Direct Message (Encrypted 1:1)
All libp2p connections are encrypted by default (Noise or TLS 1.3). For additional privacy:
// Open an encrypted stream with an application-specific protocol
stream, _ := host.NewStream(ctx, peerID, "/agent/private/1.0.0")
// All data on this stream is encrypted end-to-end
// Plus the multiaddr encryption from the underlying transport
Best for: Private negotiations, payment channel setup, sensitive data exchange.
4.6 Broadcast (All Agents Hear)
GossipSub with flood publishing ensures all connected peers receive the message.
Flood Publish (GossipSub v1.1+): - Publisher sends message to ALL scored peers, not just mesh neighbors - Counteracts eclipse attacks - Ensures maximum propagation speed
Publisher ──▶ Mesh Peer 1 ──▶ Mesh Peer 2 ──▶ ...
         ──▶ Mesh Peer 3 ──▶ Mesh Peer 4 ──▶ ...
         ──▶ Gossip Peer 5 (IHAVE) ──▶ Peer 6 (IWANT) ──▶ ...
         ──▶ Gossip Peer 7 (IHAVE) ──▶ Peer 8 (IWANT) ──▶ ...
Best for: Emergency alerts, network-wide configuration changes.

5.2 Smart Contracts for Agent Agreements
Agents use smart contracts to formalize business agreements:
Contract Components: - Parties: Agent A PeerID, Agent B PeerID - Scope: What work will be done - Payment: Amount, token, trigger conditions - Escrow: Funds locked until delivery verified - Dispute Resolution: BFT Council or oracle - Penalty: Slashing conditions for non-delivery
Flow: 1. Agent A and B negotiate terms via encrypted libp2p stream 2. Both sign a smart contract transaction 3. Payment funds are escrowed on-chain 4. Agent B performs the work 5. Agent A verifies the result 6. Smart contract releases payment
5.3 x402 Protocol for Agent Payments
x402 (by Coinbase) is an open payment protocol that enables instant, automatic stablecoin payments directly over HTTP using the HTTP 402 Payment Required status code.
How x402 Works:
1. Agent A requests service from Agent B
   GET /api/service

2. Agent B responds with payment requirement
   HTTP/1.1 402 Payment Required
   PAYMENT-REQUIRED: {
     "scheme": "x402",
     "network": "base",
     "maxAmountRequired": "1000000",  // in base units
     "resource": "https://api.agent-b.eth/service"
   }

3. Agent A constructs payment and re-requests
   POST /api/service
   PAYMENT-SIGNATURE: {
     "version": "1.0",
     "scheme": "x402",
     "network": "base",
     "payload": {
       "signature": "0x...",  // EIP-3009 or Permit2
       "paymentDetails": {...}
     }
   }

4. Agent B verifies payment on-chain and delivers service
   HTTP/1.1 200 OK
   { "result": "..." }
Key Features for Agents: - No accounts/KYC: Wallet-based payments - Micro-payments: Fractions of a cent viable - AI-friendly: Designed for machine-to-machine transactions - Multi-network: EVM and Solana support - ERC-20 support: Any token via Permit2
Integration with libp2p: x402 operates at the application layer over libp2p streams. The HTTP semantics are mapped to libp2p protocol identifiers:
/libp2p/x402/1.0.0/payment-required
/libp2p/x402/1.0.0/payment-verify

6. Scaling P2P Agent Networks
6.1 Scaling Dimensions
6.2 47 Agents: Easy
At 47 agents, the network is simple: - Each agent can maintain direct connections to most others - DHT routing tables are small and converge quickly - GossipSub meshes form rapidly - Bootstrap via mDNS + 3-5 bootstrap nodes - No bandwidth concerns
6.3 47,000 Agents: Moderate
At 47,000 agents, scaling considerations emerge:
DHT Performance: - Lookup hops: O(log n) = ~16 hops in worst case, but typically 4-5 - Each hop: parallel alpha=10 requests - Lookup time: typically 1-3 seconds globally - Routing table: Still only ~160 entries (k-buckets, not n)
GossipSub Optimizations: - Topic sharding: Split large topics into sub-topics - Lazy-pull (v2.0): Reduces bandwidth by ~50% - Peer scoring: Ensures mesh quality despite scale - IHAVE limits: Prevent gossip floods
Bandwidth per Agent: - Direct mesh: ~6 peers x heartbeat = minimal - Gossip: Proportional to topic count, not network size - DHT maintenance: ~10 min refresh cycles - Total: ~10-100 KB/s per agent (depending on topic activity)
6.4 4.7 Million Agents: Hard
At millions of agents, careful engineering is required:
DHT Considerations: - Routing tables still O(log n) in entries (~160 max) - Lookup hops increase to ~20-22 - Lookup time: 3-10 seconds for global queries - Bootstrapping: Requires large bootstrap network (1000+ nodes)
GossipSub at Scale: - Topic explosion: Millions of agents subscribing to many topics - Solution: Hierarchical topic naming: /agents/region/us-east/capabilities/nlp   /agents/region/eu-west/capabilities/vision   /agents/global/emergency - Mesh quality: Peer scoring becomes critical - Bandwidth: Each agent only cares about its topics, not all agents
Bandwidth Estimates (per agent):
Storage per Agent: - DHT routing table: ~50 KB - GossipSub message cache: ~10 MB (configurable) - Peer store (known peers): ~1-10 MB - Reputation data: ~1 MB (local subset) - Total: ~20 MB baseline

7.2 Sybil Attacks
Attack: One bad actor spawns thousands of agent identities to control the network.
Impact on DHT: - Sybils flood routing tables - Attackers can intercept/modify DHT queries - Content can be censored or redirected
Defenses:
In libp2p: The DHT implements IP diversity filters and routing table constraints. Applications can add proof-of-work for PeerID generation.
7.3 Eclipse Attacks
Attack: An attacker fills a victim’s routing table with malicious nodes, isolating the victim from the legitimate network.
Impact: - Victim cannot find legitimate peers - DHT lookups are controlled by attacker - Content requests are censored or redirected
Defenses: - Disjoint lookups: Multiple independent lookup paths - Bootstrap diversity: Multiple well-known bootstrap nodes - Churn: Periodically leave and rejoin via trusted bootstraps - Routing table auditing: Check if neighbors have suspicious connection counts - Proximity constraints: Don’t fill routing table with similar IPs
Key insight: “Similar to the Byzantine Generals Problem, given enough colluding attackers, defense becomes impossible for many P2P attacks.” The goal is to make attacks prohibitively expensive.
7.4 Replay Attacks
Attack: An attacker captures valid messages and retransmits them later.
Defenses: - Challenge freshness: Every authentication includes a timestamp; challenges expire in <=300 seconds - Nonces: Each message includes a unique nonce; duplicate nonces are rejected - Session binding: Session context includes verifier identity, preventing cross-verifier replay - Stream sequence numbers: GossipSub v2.0 uses sequence numbers within streams - ratify-protocol: session_context binding includes verifier’s public key ID
7.5 Man-in-the-Middle on P2P Connections
Attack: An attacker intercepts and potentially modifies communications between two agents.
Defenses (all built into libp2p): - Noise Protocol: All libp2p connections use Noise XX handshake by default - PeerID verification: PeerIDs are self-certifying (hash of public key) - TLS 1.3: Alternative secure transport with certificate-based verification - Perfect Forward Secrecy: Session keys cannot be recovered from long-term keys - Stream multiplexing: Each protocol runs on its own encrypted substream
Result: MITM is cryptographically infeasible without breaking Ed25519 or the Noise protocol.
7.6 How BFT Council Prevents Malicious Agents
The BFT (Byzantine Fault Tolerant) Council pattern (as implemented by councilof.ai) provides a defense-in-depth mechanism:
Architecture: - 33 agents form a BFT Council - Any verdict requires a supermajority (e.g., 5-of-5 or 22-of-33) - Each “queen” (council member) rotates through different LLM providers - BLS threshold signatures: One aggregate signature, multiple independent signers
Verdict Flow: 1. A dispute or critical decision is submitted to the Council 2. Each council member independently deliberates 3. Members vote and sign their verdict 4. BLS threshold signature aggregation produces a single verifiable signature 5. Verdict is published to the proofof.ai receipt ledger
Security Properties: - Tolerates up to f malicious members where n = 3f + 1 (33 tolerates 10) - Even 2 simultaneous failures in a 5-of-5 council leave a 3-of-5 quorum - Dissent is recorded (minority opinions published with reasoning) - Every verdict is independently auditable
Integration with P2P Agent Networks: - Critical transactions (high-value, disputed) go through BFT Council - Routine transactions use direct agent-to-agent with reputation - Council acts as the “court of last resort” for the agent network - Verdicts are gossiped via GossipSub for network-wide awareness

import { tcp } from '@libp2p/tcp'

import { bootstrap } from '@libp2p/bootstrap'
import { gossipsub } from '@chainsafe/libp2p-gossipsub'

// Create agent node with full libp2p stack
const createAgentNode = async (bootstrapList = []) => {
  const node = await createLibp2p({
    addresses: {
      listen: ['/ip4/0.0.0.0/tcp/0']
    },
    transports: [tcp()],
    connectionEncryption: [noise()],
    streamMuxers: [yamux()],
    peerDiscovery: bootstrapList.length > 0 
      ? [bootstrap({ list: bootstrapList })] 
      : [],
    services: {
      dht: kadDHT({
        clientMode: false,  // This node participates in DHT routing
      }),
      identify: identify(),
      pubsub: gossipsub({
        allowPublishToZeroTopicPeers: true,
        // Enable peer exchange for mesh discovery
        doPX: true,
      }),
    },
  })
  return node
}

// Agent 1: Bootstrap node (known address)
const agent1 = await createAgentNode()
await agent1.start()
const agent1Multiaddr = agent1.getMultiaddrs()[0].toString()
console.log(`Agent 1 listening on: ${agent1Multiaddr}`)

// Agent 2: Connects via bootstrap
const agent2 = await createAgentNode([agent1Multiaddr])
await agent2.start()
console.log(`Agent 2 started with PeerID: ${agent2.peerId}`)

// Agent 2 discovers Agent 1 via bootstrap
agent2.addEventListener('peer:discovery', (evt) => {
  console.log(`Agent 2 discovered: ${evt.detail.id.toString()}`)
})

// Agent 2 stores its capability in the DHT
const capabilityKey = new TextEncoder().encode('capability:nlp')
const capabilityValue = JSON.stringify({
  peerId: agent2.peerId.toString(),
  capabilities: ['text_summarization', 'translation'],
  timestamp: Date.now(),
})

// Wait for DHT to be ready, then store
await new Promise(r => setTimeout(r, 5000))
await agent2.services.dht.put(capabilityKey, new TextEncoder().encode(capabilityValue))
console.log('Agent 2 published capability to DHT')

// Agent 1 searches for NLP capability
const providers = []
for await (const event of agent1.services.dht.get(capabilityKey)) {
  if (event.name === 'VALUE') {
    const record = JSON.parse(new TextDecoder().decode(event.value))
    console.log(`Found capability provider: ${record.peerId}`)
    console.log(`Capabilities: ${record.capabilities.join(', ')}`)
    providers.push(record)
  }
}

// Agent 1 directly connects to Agent 2
if (providers.length > 0) {
  // Use DHT to find the peer's multiaddrs
  const peerInfo = await agent1.services.dht.findPeer(
    providers[0].peerId
  )
  await agent1.dial(peerInfo)
  console.log(`Agent 1 connected to Agent 2 directly!`)
}

const createAgent = async (bootstrapList, agentName) => {
  const node = await createLibp2p({
    addresses: { listen: ['/ip4/0.0.0.0/tcp/0'] },
    transports: [tcp()],
    connectionEncryption: [noise()],
    streamMuxers: [yamu()],
    peerDiscovery: [bootstrap({ list: bootstrapList })],
    services: {
      pubsub: gossipsub({
        allowPublishToZeroPeers: true,
        // Flood publish for maximum propagation
        floodPublish: true,
        // Enable peer exchange
        doPX: true,
        // Sign all messages for authentication
        signMessages: true,
        strictSigning: true,
      }),
    },
  })

  // Subscribe to agent status topic
  const topic = 'agents/status'
  await node.services.pubsub.subscribe(topic)

  // Handle incoming status messages
  node.services.pubsub.addEventListener('message', (evt) => {
    const msg = JSON.parse(new TextDecoder().decode(evt.detail.data))
    console.log(`[${agentName}] Received status from ${msg.agent}: ${msg.status}`)
  })

  // Broadcast own status every 10 seconds
  setInterval(async () => {
    const status = {
      agent: agentName,
      peerId: node.peerId.toString(),
      status: 'available',
      load: Math.random(),
      timestamp: Date.now(),
    }
    await node.services.pubsub.publish(
      topic,
      new TextEncoder().encode(JSON.stringify(status))
    )
    console.log(`[${agentName}] Published status`)
  }, 10000)

  return node
}

// VerifyAgentIdentity checks a ProofBundle from an agent
func VerifyAgentIdentity(bundle *ratify.ProofBundle, ctx *AgentContext) (*ratify.VerificationResult, error) {
    verifier := ratify.NewVerifier(
        ratify.WithRevocationProvider(ctx.RevocationList),
        ratify.WithTrustedKeys(ctx.TrustedKeys),
        ratify.WithChallengeWindow(300 * time.Second), // 5 min freshness
    )
    
    result, err := verifier.Verify(bundle, ratify.VerifierContext{
        Now: time.Now().Unix(),
        InvocationsInWindow: func(certID string, windowS int64) int {
            // Rate-limiting check
            return getRecentInvocationCount(certID, windowS)
        },
    })
    
    if err != nil {
        return nil, err
    }
    
    // Check result
    switch result.IdentityStatus {
    case "authorized_agent":
        log.Printf("Agent %s authorized with scope: %v", 
            result.AgentID, result.GrantedScope)
        return result, nil
    case "revoked":
        return nil, fmt.Errorf("agent certificate has been revoked")
    case "expired":
        return nil, fmt.Errorf("agent certificate expired")
    default:
        return nil, fmt.Errorf("verification failed: %s", result.IdentityStatus)
    }
}

"""
Kademlia DHT Demo: Agent Capability Discovery
"""
import asyncio
import hashlib
import json
from libp2p import new_host
from libp2p.peer.peerinfo import info_from_p2p_addr
from multiaddr import Multiaddr

async def capability_server(bootstrap_addrs=None):
    """Agent that advertises its capabilities on the DHT"""
    host = new_host()
    await host.get_network().listen(Multiaddr("/ip4/0.0.0.0/tcp/0"))
    
    # Connect to bootstrap peers
    if bootstrap_addrs:
        for addr in bootstrap_addrs:
            info = info_from_p2p_addr(Multiaddr(addr))
            await host.connect(info)
    
    print(f"Capability server running at: {host.get_addrs()[0]}")
    print(f"PeerID: {host.get_id()}")
    
    # Store capability record
    capability = {
        "peer_id": str(host.get_id()),
        "capabilities": ["image_generation", "video_editing"],
        "version": "1.0",
        "timestamp": time.time(),
    }
    
    capability_key = hashlib.sha256(b"capability:image").digest()
    capability_value = json.dumps(capability).encode()
    
    # Put value into DHT
    await host.get_dht().put_value(capability_key, capability_value)
    print("Capability advertised on DHT")
    
    # Keep running
    while True:
        await asyncio.sleep(60)
        # Re-publish periodically
        await host.get_dht().put_value(capability_key, capability_value)

async def capability_client(bootstrap_addrs):
    """Agent that searches for capabilities on the DHT"""
    host = new_host()
    await host.get_network().listen(Multiaddr("/ip4/0.0.0.0/tcp/0"))
    
    # Connect to bootstrap
    for addr in bootstrap_addrs:
        info = info_from_p2p_addr(Multiaddr(addr))
        await host.connect(info)
    
    # Wait for DHT to bootstrap
    await asyncio.sleep(2)
    
    # Search for image generation capability
    capability_key = hashlib.sha256(b"capability:image").digest()
    
    try:
        value = await host.get_dht().get_value(capability_key)
        record = json.loads(value.decode())
        
        print(f"Found agent: {record['peer_id']}")
        print(f"Capabilities: {record['capabilities']}")
        
        # Find the peer's multiaddrs via DHT peer routing
        peer_info = await host.get_dht().find_peer(record['peer_id'])
        
        # Connect directly
        await host.connect(peer_info)
        print(f"Connected to capability provider!")
        
    except Exception as e:
        print(f"Capability lookup failed: {e}")

// BFT Council arbitration for disputed agent transactions
package main

import (
    "context"
    "fmt"
    "time"
)

// BFTCouncil represents the 33-agent arbitration council
type BFTCouncil struct {
    Members    []CouncilMember  // 33 members
    Threshold  int              // Minimum for quorum (e.g., 22)
}

type CouncilMember struct {
    PeerID    string
    PublicKey BLSPublicKey
    LLMProvider string  // Rotates: OpenAI, Anthropic, Google, etc.
    Hat       string    // STRICT, BALANCED, LIGHTWEIGHT (rotates weekly)
}

type DisputeCase struct {
    ID          string
    Plaintiff   string    // Agent PeerID
    Defendant   string    // Agent PeerID
    Evidence    []Evidence
    RequestedAction string
    StakedAmount    float64
}

// SubmitDispute sends a case to the BFT Council
func (c *BFTCouncil) SubmitDispute(ctx context.Context, dispute *DisputeCase) (*Verdict, error) {
    // Broadcast dispute to all council members via GossipSub
    topic := "/csoai/bft/cases"
    disputeMsg, _ := json.Marshal(dispute)
    
    // Each council member independently deliberates
    responses := make(chan CouncilVote, len(c.Members))
    
    for _, member := range c.Members {
        go func(m CouncilMember) {
            vote := m.Deliberate(dispute)
            responses <- vote
        }(member)
    }
    
    // Collect votes with timeout
    var votes []CouncilVote
    timeout := time.After(30 * time.Second)
    
    for i := 0; i < len(c.Members); i++ {
        select {
        case vote := <-responses:
            votes = append(votes, vote)
        case <-timeout:
            break
        }
    }
    
    // Aggregate BLS threshold signature
    verdict := c.AggregateVerdict(votes)
    
    // Publish verdict to proofof.ai receipt ledger
    receipt := c.CreateReceipt(verdict)
    c.PublishReceipt(receipt)
    
    return verdict, nil
}

// VerifyVerdict checks a BFT Council verdict
func (c *BFTCouncil) VerifyVerdict(verdict *Verdict) bool {
    // Verify BLS aggregate signature
    return bls.VerifyAggregate(verdict.AggregateSignature, c.AggregatePublicKey, verdict.Hash())
}
