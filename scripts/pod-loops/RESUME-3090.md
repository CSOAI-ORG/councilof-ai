# Resuming the 3090 (rp-3090-now, pod `fpowppss5ngtkw`)

The script is `scripts/ops/resume-3090.sh`. It runs on the operator's machine, not on the pod. Every step checks state before it acts, so running it twice is safe. A second run after a partial one does only what is left. This file lists the same steps and gives the reason for each.

**It lands one bundle, named: `~/lanes/cross-ledger-usdc-20260925.bundle` on Oracle (branch `lane/cross-ledger-usdc-20260925`).** It never globs `~/lanes/*.bundle`. `~/lanes/claim-entity-decode.bundle` (branch `claims/extractor-decode-once-20260925`) is **held for an owner ruling**. It fails a frozen-reference gate on purpose, and no script may land it.

## Where things land after the resume

- `cross-ledger.sh` runs daily at 04:20Z. Output goes to `out/cross-ledger/usdc-<date>.json` and its proofs. When all seven core ledgers were READ, it pushes branch `ledger/auto-<date>`. `mill-hourly-land.sh` lands that branch at :50, but **only** when two things hold: the loop's OK receipt names the branch, and the branch's net diff only **adds** `public/interop/cross-ledger-usdc-<same date>{.json,/*.json}`. The 2026-09-25 file comes from this lane, so a 2026-09-25 run on the pod logs `HOLD already-on-master`, because a dated artifact is never rewritten.
- `hitl-probe-weekly.sh` runs Sundays at 05:30Z. Output goes to `out/hitl-probe/<date>/`. It finds its bank by sha256 `5043ce0b…` under `out/effect-binding-server-*`, or at `HITL_BANK`. It publishes nothing.
- `garak-weekly.sh` runs Sundays in the :27–:40 slots, only with a GPU. Output goes to `out/garak/<date>/`. The venv is rebuilt under `/root/lanes/garak/.venv` from the wheel in `state/garak-wheelhouse`, whose sha256 is checked. It publishes nothing.

## Offload location (backup volume)

`/workspace` on this pod is local, not a network volume, and was 96% full on 2026-09-22. Large outputs that must outlive the pod go to the network volume **`csoai-backup-ro`** (`u6bcx7p3uc`, 150 GB, EU-RO-1). It is mounted on CPU pod `dgj6roe9sazwsd` (ssh `213.173.105.108:24817`; the Mac's runpodctl key and the pod mirror key are both authorised there). Each item is stored as `/workspace/offload/<name>` with `<name>.sha256` beside it, and the sha256 is read back after the copy.

**Python packages.** If a loop fails with ModuleNotFoundError after a restart, reinstall into the persistent path: `python3 -m pip install --root-user-action=ignore --target /workspace/tools/pylib -r scripts/pod-loops/requirements-pod.txt` (lib.sh exports PYTHONPATH to it).

**CPU-only start is for copying data only.** When the host GPU is taken, the console offers "Start Pod using CPUs": that container has a 512 MB memory cgroup (despite `free` showing 251 GB), no GPU, and its /root is wiped on every restart. Do not start the scheduler there; copy data off, then migrate ("Automatically migrate your Pod data") or restart when the GPU frees.
